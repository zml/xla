# XLA:GPU Metal Backend

## Goal

Add Metal as an XLA:GPU backend so XLA keeps using the existing GPU
infrastructure for HLO optimization, fusion, buffer assignment, thunk emission,
and PJRT integration, while the Metal backend generates Apple AIR kernels
directly and links them into `.metallib` payloads for the Metal runtime.

This backend must not depend on Metal Performance Shaders for XLA kernel
execution. Collectives are also out of scope for the initial implementation.

## Backend Shape

Metal should be added as a new StreamExecutor GPU platform, alongside CUDA,
ROCm, and SYCL:

- `xla/stream_executor/metal` owns the Metal platform, executor, stream, event,
  kernel, and device-description code.
- `xla/service/gpu/metal_gpu_compiler.*` owns XLA:GPU compiler registration for
  the Metal platform.
- `xla/pjrt/gpu/se_gpu_pjrt_compiler_metal_registration.cc` registers Metal
  with the StreamExecutor PJRT GPU compiler path.
- The PJRT C API GPU plugin links Metal support when the Metal build is enabled.

The public platform name should be `metal`; the internal StreamExecutor platform
id should be `METAL`.

## Direct AIR Codegen

The desired codegen path is direct AIR generation:

1. XLA:GPU lowers HLO into the normal GPU fusion and thunk pipeline.
2. The Metal backend consumes the scheduled/fused kernel model before
   NVVM/PTX/ROCDL lowering and emits textual AIR LLVM IR directly.
3. The AIR emitter writes Metal ABI metadata (`!air.kernel`, argument
   descriptors, language/version metadata, resource limits, and compile
   options) rather than MSL source.
4. The compiler invokes Apple's Metal toolchain:

   ```sh
   air-as kernel.air.ll -o kernel.air
   air-opt --O3 kernel.air -o kernel.opt.air
   metallib kernel.opt.air -o kernel.metallib
   ```

5. The resulting `.metallib` bytes are stored in the existing opaque kernel
   binary payload used by `GpuExecutable` and kernel thunks.
6. The Metal StreamExecutor loads those bytes at runtime via
   `newLibraryWithData:error:`.
7. Kernel launch uses normal XLA:GPU launch dimensions mapped to Metal
   `dispatchThreadgroups:threadsPerThreadgroup:`.

The implementation must not use MPS for XLA kernel execution, and should not use
SPIR-V, DXIL, PTX assembly, or MSL as an intermediate for the primary path. AIR
is a private Apple format, so every emitted construct must be backed by
toolchain-generated reference AIR and validated against `air-as`, `air-opt`, and
`metallib` on the target Xcode/Metal toolchain.

Current implementation status:

- Metal StreamExecutor and PJRT plugin registration are wired on macOS.
- The runtime can compile UTF-8 MSL source directly with Metal
  `newLibraryWithSource`, and now also loads compiled `.metallib` payloads with
  `newLibraryWithData`.
- The initial compiler bridge still emits MSL from the LLVM GPU IR that XLA
  already produces for simple straight-line kernels and the common single
  bounds-check block shape used by elementwise fusions. This is now a migration
  fallback, not the target architecture.
- Library-backed GEMM rewrites are disabled for Metal so dots stay on the
  generic loop/fusion path unless the direct AIR matmul emitter recognizes and
  replaces them.
- FFT HLOs are expanded in the Metal compiler to direct DFT dot kernels before
  thunk emission. This is a correctness-first path and is not intended to be
  the long-term high-performance FFT implementation.
- A direct AIR feasibility experiment exists for fast FP32 matmul and
  matmul+ReLU, including simdgroup matrix intrinsics and Metal ABI metadata.

## Kernel ABI

Use an AIR ABI generated by XLA. Buffer arguments map to AIR address spaces and
resource metadata:

```llvm
define void @xla_kernel(
    ptr addrspace(1) "air-buffer-no-alias" %arg0,
    ptr addrspace(1) "air-buffer-no-alias" %arg1,
    <3 x i32> %threadgroup_id,
    <3 x i32> %thread_id) #0 {
  ...
}

!air.kernel = !{!0}
!0 = !{ptr @xla_kernel, !1, !2}
!2 = !{!3, !4, !5, !6}
!3 = !{i32 0, !"air.buffer", !"air.location_index", i32 0,
       i32 1, !"air.read_write", !"air.address_space", i32 1}
!4 = !{i32 1, !"air.buffer", !"air.location_index", i32 1,
       i32 1, !"air.read_write", !"air.address_space", i32 1}
!5 = !{i32 2, !"air.threadgroup_position_in_grid"}
!6 = !{i32 3, !"air.thread_position_in_threadgroup"}
```

Rules:

- XLA buffer arguments are assigned to consecutive Metal buffer indices.
- Global memory maps to AIR address space 1.
- Constant buffer records map to AIR address space 2 when they are not embedded
  directly.
- Threadgroup memory maps to AIR address space 3.
- Barriers map to AIR barrier intrinsics such as `air.wg.barrier`.
- XLA block dimensions map to Metal threadgroups per grid.
- XLA thread dimensions map to Metal threads per threadgroup.
- Thread IDs, threadgroup IDs, grid IDs, and simdgroup IDs are represented as
  synthetic AIR function arguments annotated with the corresponding AIR metadata
  (`air.thread_position_in_threadgroup`, `air.threadgroup_position_in_grid`,
  `air.thread_position_in_grid`, `air.simdgroup_index_in_threadgroup`).

Scalar kernel parameters are not required for the first XLA-generated kernel
path. If a hand-written or custom kernel requires scalar parameters, the runtime
must distinguish them from buffer addresses before accepting that kernel.

## Runtime MVP

The runtime MVP should use shared `MTLBuffer` allocations so XLA device address
arithmetic can be represented with host-visible pointer ranges:

- `MetalExecutor::Allocate` creates a shared `MTLBuffer`.
- The executor records base pointer, size, and `MTLBuffer` in an allocation map.
- Kernel launch resolves each XLA device address to `MTLBuffer + offset`.
- H2D, D2H, and D2D copies are implemented with host copies for shared buffers.
- `BlockHostUntilDone` waits for the last submitted command buffer.

Private Metal buffers, heaps, blit encoders, and more precise memory placement
can be added after correctness is established.

## Unsupported In MVP

The first backend version should fail clearly for:

- Collectives and collective memory.
- NCCL/NVSHMEM-equivalent behavior.
- MPS, BLAS, DNN, and vendor library custom calls.
- Triton codegen.
- Command buffers.
- Peer access.
- Multi-host execution.

The Metal compiler should disable GPU passes that would introduce library calls
or non-AIR codegen paths. Dot and convolution should initially lower through
generic fused loops when supported by the direct AIR emitter, with recognized
matmul patterns moving to explicit simdgroup AIR kernels.

## Build And Registration

Metal should be opt-in and macOS-only at first. The build should link the Metal
runtime implementation with:

- `Foundation.framework`
- `Metal.framework`

The PJRT C API GPU plugin build target is:

```sh
bazel build //xla/pjrt/c:pjrt_c_api_gpu_plugin
```

When Metal is enabled, that target should pull in:

- the Metal StreamExecutor platform,
- the Metal XLA:GPU compiler registration,
- the generic GPU transfer manager,
- the StreamExecutor PJRT GPU compiler registration for Metal.

## Test Plan

Start with build and registration tests:

- Metal platform id is unique and registered.
- Metal compiler factory registration succeeds.
- PJRT platform mapping recognizes `metal`.
- The PJRT C API GPU plugin links with Metal support on macOS.

Then add runtime tests on macOS with a Metal-capable GPU:

- Device enumeration.
- Stream creation.
- Shared-buffer allocation and deallocation.
- H2D, D2H, and D2D copies.
- Memset.
- Hand-written `.metallib` vector-add kernel loaded through `KernelLoaderSpec`.

Finally add XLA end-to-end tests:

- elementwise fusion,
- broadcast,
- copy/transpose,
- reduction,
- small dot through generic loop lowering,
- recognized FP32 matmul through simdgroup AIR lowering,
- recognized FP32 matmul+ReLU through simdgroup AIR lowering,
- direct FFT expansion coverage for FFT/IFFT/RFFT/IRFFT.

## Direct AIR Feasibility Spike

Apple's Metal toolchain can assemble textual AIR LLVM IR directly:

```sh
air-as matmul_air_direct.ll -o matmul_air_direct.air
air-opt --O3 matmul_air_direct.air -o matmul_air_direct.opt.air
metallib matmul_air_direct.opt.air -o matmul_air_direct.metallib
```

A repo-local experiment lives in `xla/service/gpu/metal_air_experiment`.
It contains:

- an MSL reference kernel that emits textual AIR with `metal -S -emit-llvm`,
- a hand-authored textual AIR FP32 matmul kernel using simdgroup matrix
  intrinsics,
- a small Objective-C++ runner that loads the metallib, validates the result,
  and reports Metal GPU timestamps.

On an Apple M3 Max, the hand-authored AIR path validates a
2048x2048x2048 FP32 matmul and reaches about 2.9 TFLOP/s after `air-opt --O3`.
The same experiment also validates a fused matmul+ReLU epilogue by applying a
vector compare/select to the simdgroup accumulator before the matrix store.
This proves that direct AIR is technically viable for at least one fast compute
kernel with a simple fused epilogue. The AIR contract is still private and
version-specific, so this should remain an experimental path until we understand
metadata stability, compiler versioning, and runtime ABI requirements across
Xcode/macOS releases.

## Direct AIR Implementation Plan

The migration should happen in small commits so the plugin keeps building:

1. Runtime library loading:
   - Accept compiled `.metallib` bytes in the existing opaque kernel binary
     payload.
   - Detect the `MTLB` magic and load those bytes with `newLibraryWithData`.
   - Keep source fallback only while the current MSL bridge still exists.

2. Toolchain wrapper:
   - Add a Metal AIR compilation helper that finds `air-as`, `air-opt`, and
     `metallib` from an explicit debug option or the developer toolchain.
   - Feed textual AIR through `air-as`, then `air-opt --O3`, then `metallib`.
   - Dump `.air.ll`, `.air`, optimized `.air`, and `.metallib` artifacts when
     XLA dumping is enabled.

3. AIR module emitter:
   - Emit module header, target triple, data layout, module flags,
     `!air.version`, `!air.language_version`, and `!air.compile_options`.
   - Emit one AIR function per XLA kernel with `!air.kernel` metadata.
   - Generate buffer/constant/thread/simdgroup argument descriptors from the
     XLA kernel thunk ABI.
   - Generate scalar arithmetic, loads/stores, comparisons, selects, branches,
     and simple loops from the fused kernel expression tree.

4. Correctness-first generic kernels:
   - Cover elementwise/broadcast/copy kernels first.
   - Cover simple reductions with explicit AIR loops and barriers.
   - Disable unsupported GPU paths with clear errors instead of silently falling
     back to CUDA/ROCm intrinsics.

5. Fast matmul path:
   - Recognize FP32 dot patterns that match row-major contiguous matmul.
   - Emit the simdgroup 8x8 AIR kernel shape proven by
     `metal_air_experiment/matmul_air_direct.ll`.
   - Support a small epilogue set first: identity, ReLU, add-bias, and
     add-bias+ReLU.
   - Keep launch dimensions aligned with the AIR kernel contract: 128 threads
     per threadgroup, four simdgroups, each threadgroup producing a 16x32
     output tile.

6. Compiler switch-over:
   - Add a Metal compiler mode that returns `.metallib` bytes from
     `CompileTargetBinary`.
   - Make the direct AIR path the default once elementwise and the recognized
     matmul+ReLU case pass end-to-end.
   - Leave the MSL bridge behind a temporary debug flag only for comparison,
     then remove it.

7. Validation:
   - Keep the standalone AIR experiment as a toolchain canary.
   - Add unit tests for AIR text generation and metadata shape.
   - Add PJRT/JAX tests for elementwise, dot, and dot+ReLU.
   - Track performance separately from correctness; matmul+ReLU should be
     benchmarked against the standalone AIR runner and the current MSL fallback.

## Implementation Phases

1. Land this design document.
2. Add Metal platform id and build skeleton.
3. Add a minimal Metal StreamExecutor runtime that can enumerate devices and
   reject unsupported runtime operations with clear errors.
4. Wire Metal into XLA service, transfer manager, platform util, computation
   placer, and PJRT compiler registration.
5. Make the PJRT C API GPU plugin build with Metal support.
6. Land the temporary MSL bridge for bring-up coverage.
7. Add runtime loading for `.metallib` payloads.
8. Add the AIR toolchain wrapper and direct AIR module emitter.
9. Move correctness kernels from MSL bridge to direct AIR.
10. Add fast direct AIR matmul and matmul+ReLU lowering.
11. Make direct AIR the default and retire the MSL bridge.
12. Expand supported HLO coverage and improve memory placement/performance.
